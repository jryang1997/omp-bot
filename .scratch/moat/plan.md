# omp-bot 护城河计划（初稿）

2026-10-16。来源是 J3rry 的团队调研包 `ai-assistant-landscape-20261016`（89 个候选，18 个开源产品源码深读，商业产品看官方资料）。关键源码摘录放在 `excerpts/`，每份都带固定提交的原始链接。调研没有运行任何候选，下面说的别家机制都是静态读源码的结论。

## 一句话打法

调研的核心结论是：强助理的差距已经不在模型回合里，而在回合之外。用户离开、子任务结束、服务重启、撤权、发信结果不明时，谁保存事实、谁有权继续、谁确认完成。

omp-bot 的路线不变：回合内的事全交给 OMP，回合外的四本账由我们补。

- **OMP 已经有的，直接用，不重建：** 子代理和并行（`task`，含 worktree 隔离、持久恢复）、目标和预算（`goals`，含无进展自动停）、秘密替身（`secrets`，模型只看到占位符）、技能、记忆后端（mnemopi）、自学习（`autolearn`，实验中）、后台任务（`async`）、检查点。
- **我们补的四本账**（调研第 8 节）：
  - Work：用户要什么，怎么算验收。
  - Execution：这一次运行归谁，为什么停。
  - Effect：外部动作有没有批准，有没有发生。
  - Delivery：结果有没有送到该收的人手里。

## 我们已经有的，算进护城河

- **持久命名队友加共享电脑**，就是 Grok Bot 的形态。Grok 是同一成员的所有 Bot 共用一台电脑，没有隔离（调研 5.1）；我们每个 bot 一个 Linux 座席，主目录互相读不到，登录靠登录屏统一发布。这一格我们比 Grok 细。
- **本地优先**：数据在用户自己的 Windows 上，team 目录是 git 仓库，Markdown 和技能都能带走。调研第 7 节把"可迁移"列为切换成本的反面，对用户这是卖点。
- **恢复的雏形**：Run 台账，进程退出、超时、预算杀掉都记 `side_effect_unknown`，重启后未落定的 Run 标 interrupted，不自动重跑。这和 Hermes 的 unknown 同一个方向。
- **计划调度**：时区计算、错过记 missed 回执不补跑。
- **跨设备**：安卓配对、渠道（`/run`、取消）、桌面托盘。

## 别人的护城河，我们怎么借

按调研第 10 节的顺序排，每一步先复现一个真实失败，再改。

### 0. 基线：先把失败复现出来

挑三类真实工作固定下来（资料研究、改代码、写内容），写一个故障注入脚本，记录现在的行为：

1. A 派活给 B 时，B 正忙，现在直接报错（`message_bot` 是同步的，busy 就拒绝）。
2. B 干到一半，服务重启，A 收不到结果，也没人知道 B 做到哪。
3. 有挂起的审批时重启，审批一律变 expired。
4. 定时任务跑完了，渠道通知没发出去，界面是不是照样显示成功。这一条还没核实，先写脚本看。

验收：四个场景各有一个脚本，结果记进 `proof/baseline/`。前三条要稳定复现现在的失败，第四条如果其实没问题，就从后面的第 3 步里删掉。

### 1. 异步派工树（借 OpenMausBot、Orca、Hermes）

**别人怎么做：**
- OpenMausBot 把"Head 结束一次回合"和"交给 Head 的活做完了"分开。派工写 SQLite，父任务有子任务没交回就进 waiting，全部交回后 resume，让负责人接回验收（`excerpts/P1-OM4.md`）。
- 重启按深度从子到父恢复。已派出子任务的继续等；有外部动作的中断任务不自动重跑；其他的最多重跑一次（`excerpts/P1-OM5.md`）。
- 每个 tick 都重查权限，撤权后结果不能越界交回（`P1-OM4.md` 第 257 行）。
- Orca 把 worker 的完成报告当一条要核实的协议消息，读回不一致就报 operation_unknown（调研 4.2）。
- Hermes 把执行状态和交付状态分两本账，交付用 claim 加租约，次数用完记 dropped，结果仍可查（`excerpts/P1-HE8.md`）。

**我们怎么落：**
- 新增"派活"：`message_bot` 加一个异步方式（或新工具 `assign_work`），写一条 Work（父 Run、验收标准、截止时间）。目标 bot 忙就排队，不拒绝。
- 父回合可以先结束，进入等待。子任务交回时写一条 Delivery，父 bot 下一轮被唤醒（用 OMP 的 `follow_up`），由它验收。
- 重启恢复照 OpenMausBot 的三条规则。交回前重查目标 bot 是否还对这个会话可见。
- bot 内部的并行拆分继续交给 OMP 的 `task`，我们不管。跨 bot 才走我们的派工树。

**验收：**
- 基线场景 1、2 不再出现。
- 交回前后各 kill 一次服务，结果回到原父任务，重复交付不重复结案。

### 2. 外部动作账（借 Rakazo、Paperclip、IronClaw）

**别人怎么做：**
- Rakazo 的效果键由 run、工具、规范化参数的 sha256 和同轮出现次数组成，不用模型的 tool-call id，因为重放时它会变（`excerpts/P2-RK17.md`）。
- 非只读动作执行前先写效果记录。完成的复用结果；重启时还停在 executing 的改成 uncertain，不当成没执行（`excerpts/P2-RK20.md`）。
- Paperclip 把审批绑到 agent、run、连接、工具和参数哈希上，旧审批不能授权另一组参数（`excerpts/P1-PC14.md`）。
- IronClaw 子任务交回要求父任务恰好处在等这个依赖的状态，一个子结果不能解锁另一张审批（`excerpts/P1-IR9.md`）。

**我们怎么落：**
- 只管我们自己的 host tool：`message_bot`、渠道发送、`computer_publish_file`、`computer_install_packages`、派活。OMP 原生工具（bash、edit）的审批归 OMP，我们只读它的事件。
- 台账加 effects 表：效果键、参数哈希、状态（planned、executing、done、unknown）、回执。
- 审批记录带参数哈希。重启后挂起的审批不再一律 expired：参数和权限没变就恢复同一个请求，变了就明确作废。

**验收：**
- 发出动作后 kill 服务，重启后显示 unknown，不重发。
- 批准后改参数，原批准不生效。

### 3. 交付账（借 Hermes、ZeroClaw）

**别人怎么做：**
- Hermes 的 cron 投递碰渠道前先把 pending 改成 delivering；owner 死了的 delivering 恢复成 unknown，不盲重发（`excerpts/P1-HE11.md`）。
- ZeroClaw 把调度、执行、投递分三处记（调研 3.8）。

**我们怎么落：**
- 定时任务的回执和渠道通知拆成"跑完了"和"送到了"两个状态。投递失败有次数上限，用完记 dropped，结果仍能在界面里查到。

**验收：**
- 基线场景 4 不再出现。
- 渠道断开时，界面显示"跑完了，没送到"。

### 4. 可纠正的团队记忆（借 OpenMausBot、nanobot）

**别人怎么做：**
- OpenMausBot 的团队记忆每条自动写入都先进 proposed，等管理员接受；替换旧事实时带上旧版本的 revision，期间旧事实变了就拒绝（`excerpts/P1-OM12.md`）。
- nanobot 的 Dream 按历史游标分批整理，用真实文件 diff 判断改了什么，比相信模型说"学会了"可靠。但它的内容、游标、git 提交不在一个事务里（调研 3.9）。

**我们怎么落：**
- 共识层 `team/AGENTS.md` 现在只有用户和 Main Bot 改。加一条提案通道：任何 bot 提一条团队事实，带来源；电脑面板旁边多一个"待确认"列表，用户点接受或拒绝。接受时检查 revision，写进 team 目录并自动 git 提交。
- 个人记忆仍走 mnemopi。OMP 的 `autolearn` 先评估，不急着开。

**验收：**用户纠正一条团队事实后，旧事实不再被写回；两个 bot 同时提案替换同一条，后一个被拒并提示重提。

### 5. 授权放在模型之外（借 Muse、dots，先用 OMP 的 secrets）

**别人怎么做：**
- Meta 的说法是 Muse 跑在隔离环境里，Sentinel 在外面，连接器动作和出站都过它。秘密在内部只是替身 token，放行出站时才换成真凭据（调研 5.3，厂商自述，未审计）。
- dots 的 Auto-review 在 dot 改不到的环境之外（调研 5.2）。

**我们怎么落：**
- 先打开 OMP 自带的 secrets 占位符，模型只看到占位符，执行时替换。
- 审批策略本来就在 omp-bot 宿主里，模型改不到。这一步只核实共享电脑里没有绕过宿主的出站凭据。
- 不自建 Sentinel，先记成研究项。

**验收：**会话记录和发给模型的内容里找不到真实秘密。

### 6. 整项工作的预算（借调研第 8 节，用 OMP goals）

- 预算挂在派工树的根上，子任务从父预算里扣，不各拿一份完整预算。复用 OMP goals 的预算计数和无进展自动停。
- 验收：一棵派工树超预算时整棵停，留出交回和汇总的余量。

## 明确不做

- skip: Paperclip 的组织治理（issue、公司、多级审批）。个人加几个 bot 用不上，调研第 10 节也建议等真有需求再上。
- skip: Lody 的 CRDT 同步、T3 的全套事件溯源。我们是单机单用户，SQLite 台账够用。
- skip: 自建 Manus 式宽研究。OMP 的 `task` 已经有并行子代理和新上下文。
- skip: Herdr 式终端常驻。桌面已有托盘，共享电脑关窗口不停机，先核实没有缺口再说。
- skip: 角色名、头像、群聊、时间线这类外观。调研第 7 节说它们最容易抄，不构成护城河。

## 护城河怎么讲

我们的护城河是这几样叠在一起：

1. OMP 的回合内能力。
2. 回合外的四本账：派活不丢、动作不重、审批不串、结果送到。
3. 共享电脑座席隔离加统一登录。
4. 数据在本地，随时能带走。

单看哪一样都能被抄，难抄的是全部叠在一起之后，在故障下的表现。每一步都要有故障注入的证据，不靠演示。
