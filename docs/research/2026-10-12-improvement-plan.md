# omp-bot 改进与大幅调优方案

本方案基于 [对标调研](2026-10-12-competitive-gaps.md) 和 [本机运行证据](2026-10-12-runtime-evidence.md)。当前交付为研究与设计，没有实施下列代码、数据迁移、云部署或对外集成。所有数字目标均为建议验收标准，不是已测性能。

## 产品方向与范围

目标是基于 OMP 的本地优先代理工作台。用户能创建有岗位的 Bot，交给它真实资料和任务，看见过程，批准特定动作，随时停止，得到可打开的结果，并在重启后继续管理未完成工作。

首个完整闭环采用三个工作场景。

1. 调研 Bot 读取用户提供的文档和公开网页，生成带来源的报告，交付可下载文件。
2. 开发 Bot 在用户选定项目里调查与修改，显示进度和 diff，在提交、外发或部署前停在授权边界。
3. 数据 Bot 读取 CSV 或 XLSX，运行分析，生成表格与报告，不修改源文件，输出留在工作区。

每个场景同时验收输入、执行、审批、取消、结果和故障恢复。完成这些闭环后再加入定时、飞书和远端执行。首轮不追求支付代理、电话、眼镜、完整连接器市场或企业 SSO。

## 保留与改动

保留 OMP 作为唯一主要执行引擎，保留人格、scope 会话、原生续接、压缩、RPC v2 和已有 smoke。角色 Bot 继续使用 OMP 子进程，临时子代理复用 OMP task。避免同时建立第二套模型调用、工具协议和上下文压缩机制。

修改数据与运行契约，把 Task、Run、Action、Grant、Artifact、MemoryEntry 和 Workspace 从聊天文本中分离。将私聊和群聊统一接入任务 admission 与执行管理。前端接统一事件，不再一边等待整段 HTTP reply、一边用另一条 SSE 猜同一任务状态。

不以重写前端框架作为前提。当前 vanilla JS 足够接第一轮事件和控制。复杂任务树、审批、成果与多设备状态增长后，再按模块评估 TypeScript 或 React 的维护收益。升级工具链不能当成产品功能完成的证据。

## 核心对象

| 对象 | 责任 | 建议关键字段 | 不能承担的责任 |
|---|---|---|---|
| Workspace | 项目和数据共享范围 | id、name、fileRoots、members、policyId | 用目录名字假装 OS 沙箱 |
| Bot | 常驻角色身份 | id、role、instructions、modelPreference、workspaceIds、capabilities | 每次执行的独立状态 |
| Task | 用户目标和交付标准 | id、workspaceId、ownerBotId、objective、acceptance、deadline、parentTaskId | 当作一次 LLM 回合 |
| Run | 一次执行尝试 | id、taskId、attempt、state、runtimeRef、parentRunId、budget、startedAt、finishedAt、errorKind | 对外副作用是否完成的凭空猜测 |
| Action | 待执行的具体操作 | id、runId、actor、tool、target、canonicalArgs、riskClass、status、idempotencyKey | 由模型自由改写的审批文案 |
| Grant | 已批准的范围 | id、subject、resource、verb、constraints、expiry、source、revokedAt | 全局“我同意了”布尔值 |
| Artifact | 用户可领取的结果 | id、runId、path、mime、size、hash、previewType、sourceRefs | 任意宿主文件下载入口 |
| MemoryEntry | 稳定事实与偏好 | id、scope、content、source、updatedAt、expiry、sensitivity | 不可撤销的聊天摘要 |
| Routine | 周期或事件定义 | id、ownerBotId、trigger、timezone、instructions、paused、nextRunAt、missedPolicy | 当前正在执行的 Run |

先实现实际需要的字段和状态。对象可以从简单记录起步，不要求每个对象单独服务、仓库类或插件接口。Action 的来源必须覆盖所有实际执行通路，不能只管理连接器，却让 bash、eval 或浏览器直接绕过。

Run 至少区分 queued、starting、running、waiting_input、waiting_approval、cancelling、completed、failed、cancelled。进程丢失或外部效果未知使用 interrupted 或 reconciliation_required，不自动标 completed。状态迁移由宿主真实事件驱动，不能靠模型最后一行“完成了”。

completed 表示执行结束，accepted 表示交付验收通过。两者分开。等待输入和等待审批不得当作错误反复重试。超时不得立刻回到可接新回合的 idle。

## 权限与自治

产品默认权限按操作分类，用户可在清楚的作用域内放宽。

| 操作 | 默认行为 | 用户可调范围 | 强制约束 |
|---|---|---|---|
| 已授权文档读取与公开资料调研 | 自动执行 | 文件根、资料集、域名与任务 | 不扩大到未授权项目，不允许顺带读凭据 |
| 工作区输出文件创建 | 任务授权内自动 | 输出目录、格式、数量与预算 | 不覆盖原始资料，路径必须通过后端解析与边界检查 |
| 选定项目内代码编辑 | 用户派活范围内自动 | 文件根、任务、变更类型 | 保留变更记录，离开范围或修改敏感文件另需授权 |
| 对外发消息、发布、部署、删除重要资料 | 先出具体可审查结果，再申请动作许可 | 单次或明确限时限范围授权 | 绑定接收方、目标、内容和当前输入，未答不执行 |
| 购买、资金操作、认证权限改变 | 默认交回用户或明确专门授权 | 首轮不开放自动付款 | 不把测试环境批准沿用到真实账户 |
| 内部 Bot 委派 | 同 Workspace 内自动 | 参与者和数据范围 | 子任务不得取得超过父任务的能力与预算 |
| 修改策略、扩大工具、安装扩展 | 用户专用设置流程 | 经用户查看与确认的配置 | 执行模型不能修改自己的批准记录或执行策略 |

审批卡显示谁、对什么、准备做什么、具体内容、预计费用或影响、依据哪个任务。选择至少有允许这次、拒绝、修改要求、交给我。只有能清楚表达范围的低风险操作才提供持续授权，必须显示期限并可撤销。

授权不只是一句聊天。后端保存批准对应的规范化参数或内容 hash，执行前重新检查当前 actor、资源、参数、有效期和撤销状态。参数或目标变化使批准失效。审批请求超时进入过期态，用户没有回答不能自动放行。用户更改方向时使旧批准失效。

认证权限和业务动作分开。连接 GitHub 不代表允许合并，读取飞书文档不代表允许给任何人发消息。设备离线不等于撤销权限，暂停某个 Run 不等于取消 Routine，删除 Bot 也不代表外部消息能撤回。

## 执行环境

三个环境选项必须显示真实保护强度。

- 聊天或受控读取。默认不给任意 shell、eval、网络执行和任意文件工具。使用 OMP --no-tools 配合宿主受控工具，限制明确文件根和公开请求。模型请求也属于数据发送，要披露提供商。
- 沙箱执行。文件与代码任务在专用 VM、容器或受限系统账户中执行，只挂载授权项目与输出目录。网络出口、浏览器和凭据服务在沙箱外治理。Windows 的具体实现须做真实设备原型，不假定 WSL、Docker 或 Windows Sandbox 默认存在。
- 本机完全能力。提供清楚的显式 opt-in，说明当前用户权限、工作目录不构成沙箱、已授权本机操作的范围。该选项不能被导入的 Bot 模板或模型打开。

如果设备没有经过验证的沙箱，受限模式就不提供任意代码执行。显示具体缺少什么，并给用户选择配置环境或显式本机执行。不能挂一个“安全模式”标签继续允许 bash 或 eval 访问整个主机。
三场景的环境映射明确如下。调研默认用受控读取，宿主提供限定资料的 read、公开资料 fetch/search 与文档解析。数据分析使用沙箱内的数据执行工具，开发使用沙箱或用户显式选择的本机能力模式。--no-tools 下没有内置 read 或 web_search，不能一边禁用全部工具、一边要求这些内置工具执行。

本机完全能力模式是明确的安全降级，不能保证拒绝某动作后任意代码无法绕路执行。该模式显示风险且默认不运行无人值守写任务。要求强制拒绝保证的任务必须选择受控读取或经过验证的沙箱。

`--tools`、`--no-tools`、`--no-skills`、`--no-extensions`、`--profile`、`--approval-mode` 是可用配置入口，但作用不同。profile 隔离认证与配置，tools 控制可调用接口，OS 沙箱限制实际代码，审批控制特定动作。不能把任何单个开关宣传为全部保护。

初期策略采用确定性拒绝和范围授权，独立模型只补充解释。官方 approval-mode 文档说明默认模式为 yolo，实际配置仍可能覆盖默认；原生工具审批在 --no-ui 下无法弹卡，会失败关闭。方案作两条明确选择。受控工具路径保留 headless RPC，由宿主 Action/Grant 审批。需要原生工具审批的路径使用 plain rpc-ui，移除 --no-ui，桥接 select/confirm、取消与回答帧并显式配置 approval-mode。先对打包版本做门控实验，未通过就不启用该路径，不能降级为自动放行。依据为 [审批文档](https://github.com/can1357/oh-my-pi/blob/main/docs/approval-mode.md)和 [RPC UI 协议](https://github.com/can1357/oh-my-pi/blob/main/docs/rpc.md)。

## 可复用的 OMP 接口

| 工作台需求 | 已有 OMP 入口 | 本次验证程度 | 实施边界 |
|---|---|---|---|
| 中止当前运行 | abort，另有 abort_bash、cancel_subagent | abort 调用接受 | 需验证忙碌 shell、eval、host tool 和子任务停止确认 |
| 文本与工具事件 | message_update 与 set_event_filter delta | 设置调用接受 | 需关联 runId、重连游标与已产生文本 |
| 子代理状态 | set_subagent_subscription、get_subagents | 进度订阅调用接受 | 子代理执行和 UI 树未测 |
| 新会话 | new_session | 调用接受 | 新会话不是删除旧数据，UI 要解释 |
| 模型目录 | get_available_models | 调用接受 | 认证变化后刷新，显示精确 provider/model |
| 图片输入 | prompt.images | 官方 main 文档有 | 需验证打包版本、编码、大小和模型支持 |
| 中途指令 | steer、follow_up | 官方 main 文档有 | 需验证忙时 admission 与队列行为 |
| 分支和导出 | branch、fork、export_html、get_messages_page | 官方 main 文档有 | 需验证版本与业务副作用，不能回滚外部发送 |
| 登录 | login 与 extension_ui_request | 官方 main 文档有 | --no-ui 下仅特定 login UI 请求，secret prompt 限制，需专用认证流程 |
| 凭据隔离 | auth-broker、auth-gateway | CLI help 有 | 仅确认入口，不证明覆盖模型、shell、浏览器与所有业务工具 |
| 原生审批 | plain rpc-ui 的 extension UI 与 approval-mode | 官方文档确认通道，未在本机调用验证 | --no-ui 下不能接原生审批；宿主受控工具另用 Action/Grant |
| 宿主工具取消 | host_tool_cancel.targetId | 官方文档有，当前客户端仅转发 | 每请求保存 AbortController，handler 收 signal，丢弃取消后的迟到结果，确认实际操作停止 |
| 运行预算 | goal.token_budget 与 --max-time | RPC 文档与 CLI help 有，未验证预算边界 | goal 的 RPC 续跑需要 continuationModes；只作为预算补充，不替代全体子任务费用账本 |

版本须针对 `.desktop-runtime/omp.exe` 和开发 PATH 二进制分别验证。当前探针验证的是 PATH OMP 18.10.0，不保证安装包与它始终一致。启动能力探测应记录支持版本，拒绝不兼容模式，不能静默丢弃取消或审批能力。

## 实施阶段

### 阶段一，让当前聊天可控制

目标为私聊和群聊都能看到过程、停止，并且没有超时后宿主误判 idle 的问题。

涉及 `src/rpc-client.mjs`、`src/bot.mjs`、`src/orchestrator.mjs`、`src/server.mjs`、`src/relay.mjs`、`web/app.js`、`web/index.html`、相关 smoke 和 README。

- 增加一个统一运行 id。HTTP 接受任务后返回 id，SSE 传文本、工具、子代理、等待原因和终态。
- 将 RpcClient 原生事件翻译为工作台事件，订阅底层增量。所有事件带 workspaceId、botId、scope、runId、单调 seq。
- Admission 原子覆盖启动、忙碌、取消和 draining。每个 scope 只有一条实际运行链。仅用户入口可有界排队；同步嵌套 message_bot 对忙目标继续立即拒绝，直到异步 inbox 迁移完成，防止 A→B→A 等待父回合死锁。
- 实现 stop API，覆盖 OMP、host tool、宿主解析与连接器请求、子进程和子 Run。host_tool_cancel 按 targetId 取消关联 AbortController，handler 与下游调用接 signal，迟到结果不得当作成功。不能取消的外部动作进入结果未知并对账，不能立即宣称已停止。超时与预算耗尽触发同一取消路径。
- 前端提供停止与过程面板。忙时仍能编辑草稿，发送补充指令使用明确 steering 或 follow-up。
- 增加新会话入口，把“清空显示”改成不容易误解的独立操作。
- 同步补本机 HTTP token、Origin、Host、Content-Type 校验，作为后续所有控制接口的前置条件。

验收目标为点击停止后 2 秒内显示已接受取消，实际停止完成单独显示。若底层无法在 5 秒内确认，进入停止中或阻塞并回收对应 runtime，不能假称已停止。实际停止工具的延迟需记录，不能用 UI 恢复输入替代证明。

验收还包括同 scope 两个并发输入、首轮启动期间并发、群里并发、取消中发消息、连接中断后的重连。拒绝或排队结果明确，不重复记录用户消息。完成文本不因 SSE 与 HTTP 双通道重复显示。

### 阶段二，任务、授权与运行账本

目标为工作可以在刷新和重启后被准确管理，且执行边界可检查。

- 引入 Task、Run、Action、Grant 和最小事件表。配置与历史分离，避免每个 token 改写全部 state.json。
- 推荐一个本地 SQLite 数据库承担事务、运行状态、事件游标、预算和授权记录。先验证 Node 与 Electron 内置 Node 的 node:sqlite 可用性及 Windows 打包。如不支持，再选择一个成熟兼容驱动，不为“零依赖”牺牲事务正确性。
- 先持久记录 Run 和 Action，再启动执行。提交结果后发通知。崩溃后标 interrupted 或 reconciliation_required，人工或对账完成后才恢复可能有副作用的步骤。
- 统一三类模式的明确能力集、文件范围和跨 Bot 数据共享。模型只提出动作，策略、批准和执行位于模型不可修改的控制路径。
- runtime 不能只凭 botId::scope 复用。把执行环境、权限范围与 capability 版本纳入租用兼容检查。受限 Run 禁止进入已启动的宽松进程，收紧权限必须重建或证明热更新已经生效；恢复旧 session 不恢复旧授权。每个 Run 使用最小能力，子 Run 不扩权。
- 工作台增加进行中、待我处理、完成、失败页面与任务详情，聊天里的任务卡链接到台账。
- 用量按 Run 和实际模型持久记账，预算由父任务向子任务分配，额度不因并行委派重复使用。

受控读取与沙箱模式验收拒绝后所有连接器、shell、eval、浏览器与子 Bot 都不能绕路完成动作。本机完全能力模式不承诺这种保证，须明确显示并禁用依赖该保证的无人值守流程。全部模式都要让撤销后的受控新动作停止，参数变化重新审批，过期批准不执行。测试先宽后窄的两个 Run，后者不得沿用宽权限 runtime。

恢复验收至少模拟五个崩溃点，任务写入前后、动作批准后执行前、外部动作执行后回执前、结果写入后通知前。对外副作用最多一次需要服务端幂等键或对账支持。服务不支持时保留未知状态，禁止自动重放。通知采用 outbox 与投递去重，不能用“严格 exactly once”掩盖外部系统限制。

### 阶段三，真实资料到可领取成果

目标为三个核心场景端到端可用。

- 接文件上传和图片粘贴。素材存明确 Workspace，记录 mime、size、hash 和解析状态，禁止路径穿越和混淆类型。
- 受控读取模式用宿主限定 read/fetch/search 与文档解析工具，沙箱模式在限定环境复用 OMP read 和执行工具，图像按已验证 images 协议传递。原文保留，解析失败显示具体原因，不返回假摘要。
- Artifact 目录和下载接口只提供已登记结果，检查 Workspace 授权和真实规范路径。HTML、SVG 与脚本类预览隔离，不能读取管理 token。
- 工作区文件修改前建立可回滚检查点，首先保护原始输入与用户已有变更。可使用独立快照或 shadow Git，不改变用户 Git 索引和 HEAD。精确回滚本地文件，明确不能撤销外部邮件、发布与部署。
- 接浏览器观察和人工接管。人工控制期间 Bot 停止输入，确认归还后继续。优先隔离浏览器 profile，不能默认采用用户当前可见标签或全部登录。
- 选择 GitHub 与飞书连接器，复用本机已有插件或 MCP，完成账户状态、读写权限、断连与动作记录。

验收用三份真实可公开资料和两个测试服务账户完成三个场景。资料导入、处理中断、重新打开、领取结果均可见。结果给出来源与运行验证，不以“产物非空”作为验收。

### 阶段四，持续工作与受控协作

目标为用户关窗口后仍可管理任务，重复工作无需反复派活。

- 将 Electron 窗口与 backend 生命周期分开，明确托盘、显示、退出、后台任务数量和待审批数量。
- 引入 Routine。定义时区、暂停、下一次执行、错过执行策略、结束日期、重叠执行和保留期限。默认上一轮仍活跃时跳过或合并，不产生无界队列。
- 加专用 webhook receiver，仅事件接收，验签、请求大小、重放防护与来源映射，不能暴露团队管理 API。
- 把跨 Bot 委派迁移到持久 inbox 与子 Run，保持 MAX_HOPS 及任务 lineage，增加全局并发和预算上限。
- 出错汇报协调 Bot 和用户，不自动无限重试。仅对可安全重试的失败做有界重试，认证失败与拒绝审批不重试。
- 新增 Bot 私有记忆、Workspace 共享记忆和来源引用，可查看、编辑、遗忘、导出。继续禁用用户全局共享记忆回灌。

验收为关闭窗口不终止工作，显式退出正确停止进程与释放数据锁。电脑休眠或关机后的计划显示 missed，而不是伪造执行。跨 Bot 单位任务超过预算不能继续扩散。记忆删除后召回不到旧项，原始资料是否仍保留另行明确。

### 阶段五，多渠道与可选远端执行

目标为用户通过飞书或手机触达同一套任务，不开第二个安全模型。

- 飞书 adapter 将可信用户身份映射到工作台账号和 Workspace。群聊参与者不是全部审批人，审批只能由规定身份完成。
- GUI、IM 与手机共享同一 Run 状态和授权，不跨群发送私有上下文。消息和审批回执有稳定 id 与去重。
- 首选用户常开主机或自有 VPS 作为远端节点。认证采用明确设备配对与撤销，不直接公开现有 localhost 管理接口。
- 列出远端磁盘、模型请求、浏览器登录、备份和费用边界。迁移任务需明确转移工作区、会话与凭据范围。
- 手机先完成任务查看、派活和审批，不以开发完整原生 App 为前提。

验收为同一任务从桌面发起、飞书补充、手机审批，目标和批准一致。未配对设备拒绝访问。撤销设备后不能通过保存旧 URL 继续访问。外部服务重发同一事件不重复起跑。

### 阶段六，质量、发布与扩展

- 按 run 记录首事件时间、首字时间、总耗时、任务成功与验收状态、取消确认时间、审批等待、失败分类、成本和重试。
- 做可重放的三场景验收资料，补取消、拒绝、跨域、崩溃和预算回归，保留现有真实模型 smoke。
- 检查模型与版本升级的兼容，记录实际 fallback，不隐藏因错误换模型。
- 发布前验证安装、更新、卸载保留资料、签名和依赖 provenance。原件有备份再迁移。
- 支持团队模板导入导出，默认不包含密钥、聊天、权限批准、运行状态和私有记忆。导入 Routine 默认暂停。
- 用真实需求决定企业角色、SSO、审计导出与更多平台，避免预先搭完整企业控制层。

## 大幅调优要测什么

以下是建议基线协议，不是本次调研测得数据。

| 方向 | 测量方法 | 提升手段 | 约束 |
|---|---|---|---|
| 首次派活成功 | 新数据目录，新用户完成首任务 | 认证与模板引导、错误解释 | 不能拿已有全局登录代替新用户 |
| 可感知等待 | 同模型、同端点、同输入测首事件与首字 | 真流式、工具进度、预热 | 预热必须计成本，禁止以假进度掩盖无响应 |
| Bot 资源 | 1、4、12 个 Bot 与多个 scope，记录 RSS、CPU、冷启动 | 空闲进程回收、保持会话续接、并发上限 | 不宣称进程池一定更快，先测唤醒损耗 |
| 上下文成本 | 同任务记录总 tokens、缓存与压缩 | 针对子任务精简输入、共享可引用产物 | 不丢目标、来源和审批边界 |
| 协作收益 | 单 Bot 与 2、4 workers 执行同验收 | 仅独立任务并行、冻结输入、单人集成 | 同模型实验控制变量，不以消息数作为收益 |
| 可靠性 | 超时、断网、拒绝、崩溃、恢复注入 | 事务、outbox、对账与有界重试 | 外部效果未知不得重放 |
| 审批体验 | 固定低风险与高风险场景测错误放行与无谓打断 | 窄授权、复用合法批准、明确卡片 | 不能为了少弹窗放宽不可逆动作 |
| 成本 | 每验收成功任务的实际提供商用量 | 指定 Flash 默认，按证据升级 | 账单未知写估算，记录真实 fallback |

DeepSeek V4.1 Flash 可作为用户指定的研究与 worker 模型。不要只因名字里有 Flash 就断言速度或质量。研究、代码、多模态和审批复核分别用固定资料评估，保证比较同端点、相同权限与相同验收。必要升级策略在结果失败或预算内质量不足时触发，不能静默换更贵模型。

先收至少 30 次核心任务运行的基线，区分新会话和热会话。对稀有边界用定向故障实验，不能靠 30 次成功任务估计安全性。目标可拟定为三场景正常路径均成功，故障案例全部以正确显式终态结束，越权案例全部拒绝。延迟和费用数值目标在基线后确定。

## 数据迁移与发布顺序

第一次迁移先只读盘点旧 state.json、各 scope session、persona、overlay 和 work 文件。复制原始资料到用户可找到的备份，校验可读取与文件 hash，再创建新库。保留 Bot 和 Room id，新任务不修改历史 session。迁移完成记录版本与来源，失败切回旧版本。

同时迁移 GUI、CLI、群 relay、Bot host tools、测试与 README，删除被替代的内部运行路径。对公开 CLI 用户保留既有使用能力，命令内部转成统一 Run，不要求突然更换工作流。版本升级明确说明清空、会话与删除的语义变化。

新调度、远端和扩大权限默认关闭。模板不迁移为已批准动作。升级后旧进程不能和新库并行写入。发布前使用新数据目录和旧数据备份各跑一次核心流程，再测试回退。

## 本轮裁决

先做 A、B、C、D。它们共同解决看得见、停得下、状态可信、权限可控。随后用 E 和 F 的真实场景证明产品能交付工作。G 和 H 再把可靠的闭环扩展到持续工作和多设备。

不照搬竞品的付费计划、数量限制和固定记忆行数。OpenMausBot 的 200 行或 24KB 记忆预算是一个实现样本，不是我们必须复制的正确参数。Grok 的共享电脑、Muse 的隔离 VM 和 Dots 的多执行环境也有不同取舍，按我们的本地优先目标选择。

暂不做全量 UI 重写、完整连接器市场、支付、电话和企业 SSO。主要风险是底层 OMP RPC UI 与审批覆盖、Windows 沙箱可用性、对外动作的幂等与恢复。这些必须用原型和真实执行验收解决，不能靠文档承诺。
