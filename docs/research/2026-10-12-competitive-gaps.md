# omp-bot 对标调研与重大差距清单

调研日期为 2026-10-12。对象为 OpenMausBot、Meta Muse、Grok Bot、OpenAI Dots，以及当前仓库的桌面、网页、CLI 与 Node 编排实现。本文给出判断和证据，实施方案见 [改进方案](2026-10-12-improvement-plan.md)。

## 结论

我们已有可用的 Bot 花名册、独立会话、群聊和同步委派，并复用 OMP 的真实工具与会话能力。主要差距出现在用户派活之后的完整流程。任务是否持续推进、在哪里执行、能访问什么、何时需要批准、如何停止、结果如何交付、失败如何恢复，目前没有成为统一的产品能力。

建议把产品目标设为“基于 OMP 的本地优先代理工作台”。保留多模型和本地数据优势，同时让任务、权限、运行进度和交付物成为一等对象。只继续美化聊天外观，无法追上这些竞品的核心体验。直接把用户机器暴露给更多连接器或无人值守任务，也不是合适的升级顺序。

最大十项差距按实施依赖排列。

| 顺序 | 重大差距 | 对用户的直接影响 | 建议级别 |
|---|---|---|---|
| 1 | 执行权限未独立于模型和用户全局配置 | 创建不同 Bot 并不自动限制其主机文件和工具能力 | P0 |
| 2 | 缺停止、真实取消和统一忙碌状态 | 误发、卡住或超时后不能可靠控制任务 | P0 |
| 3 | 缺持久任务与运行台账 | 长任务、重启、后台委派的责任和状态不清楚 | P0 |
| 4 | 缺流式文本、工具过程和子代理可见性 | 用户看到长时间等待，却不知道发生了什么 | P0 |
| 5 | 缺产品级授权、审批和撤销 | 无法表达“能读、能起草、发送前问我”并强制执行 | P0 |
| 6 | 缺文件输入与交付物管理 | 无法方便地交截图、文档、表格，也无法稳定领取生成文件 | P1 |
| 7 | 缺应用内连接器和浏览器接管 | 真实业务任务需要用户自己搭工具、登录和处理异常 | P1 |
| 8 | 会话续接替代了可管理的长期记忆 | 不能查看和修改 Bot 记住什么，也不能清晰隔离不同项目 | P1 |
| 9 | 缺后台生命周期、定时和事件触发 | 必须保留本机窗口，不能放心安排重复工作 | P1 |
| 10 | 多 Bot 主要靠串行聊天与同步等待 | 增加 Bot 数量不等于增加可控并行产能 | P1 |

P0 表示下一轮开发的前置项，P1 表示达到实用代理工作台必须补齐，P2 表示后续扩展。这里是产品和技术的排序，不是已确认漏洞的严重级。分报告采用的优先级口径可能不同，以本文为准。

## 调研证据与限制

五个并行研究子代理通过本次会话的 model override 指定 `magpie/commandcode-plan/deepseek/deepseek-v4.1-flash`。两条本地只读审计，三条外部产品研究。主代理核验关键源码、官方说明，并运行实际本机探针。独立上下文不等于多模型交叉验证，本次子代理均按用户要求指定同一个模型。

证据分为三种。

- 运行确认。实际本机 GUI、HTTP 请求、真实 Bot 回合或 RPC 命令的观察。
- 源码或官方文档确认。源码可判定实现，官方文档可判定产品声明。商业竞品未亲自登录实操，官方声明不能换算成实测成功率。
- 推断或未验证。架构后果、潜在攻击路径、未来效果和拟定指标。本文明确标注，不能把“没找到文档”写成“没有能力”。

本机实测最有价值的四个结果见 [运行证据](2026-10-12-runtime-evidence.md)。

1. 真正 Bot 用 read 读取工作目录外的临时文件成功，样本 n=1。它证明 cwd 不是该路径的读取边界，没有测试敏感文件读取或外传。
2. 临时服务接受非预期 Origin、Host 和 text/plain 写请求，均为 200。调用来自网络客户端，没有证明特定浏览器中的完整跨站攻击链。
3. RpcClient 的受控超时探针只发送 prompt，没有发送 abort。模型实际如何处理第二个 prompt 未测，不能宣称已复现两个模型回合重叠。
4. 本机 OMP 18.10.0 的 abort、增量事件过滤、子代理进度订阅、新会话和模型目录 RPC 调用全部成功。证明可复用接口存在，没有证明忙碌工具中止和 UI 接通后的表现。

这些产品不是同一个安全模型。OpenMausBot 更适合借鉴本地工作台，Grok Bot 更适合借鉴多 Bot 组织，Muse 更适合借鉴独立执行边界与个人目标，Dots 更适合借鉴任务管理和跨渠道持续工作。不能把四家的功能拼成一个“行业标配全都有”的虚构产品。

OpenMausBot README 对 Grok 模型的竞争性描述与 Grok 自己的文档有差异。Grok 官方明确说模型选择由 Cursor 管理，服务模型可能变化，没有用户模型选择器。因此不采用竞争对手文案里的“Grok only”作为结论。

## 我们现在的实现与保留价值

GUI 与 CLI 调用 Orchestrator。每个 `botId::scope` 创建独立 BotRuntime，通过 RpcClient 驱动 OMP 子进程。Bot 人格与隔离 overlay 写入各自目录，真实对话存在 OMP session JSONL。`state.json` 保存花名册、群、投递记录与用于显示的聊天文本。群聊由纯 Node relay 驱动。

关键定位在 `src/orchestrator.mjs:170`、`src/bot.mjs:70`、`src/rpc-client.mjs:54`、`src/persona.mjs:62`、`src/store.mjs:15`、`src/relay.mjs`。入口和 UI 在 `src/server.mjs:102`、`web/app.js`、`desktop/main.mjs:62`。

值得保留的设计有独立 scope 会话、原生续接与压缩、协议 v2、host tool、hop 上限、busy 拒绝、失败回执、本机默认监听、原子文件替换、Electron renderer 隔离和现有真实模型 smoke。它们是可继续发展的小底座。底层 OMP 已经有浏览器、子代理、技能和插件能力，不能把“工作台没有管理界面”误报为“运行时完全没有这些能力”。

| B10 | 无数据流和提供商披露界面 | 本地存储容易被误认为离线推理 | 列出模型端点、搜索、浏览器和业务服务的发送范围，不宣称完全离线 | P1 |

边界设计应采用三层。第一层是服务账号或 OAuth 自带的权限。第二层是文件系统、网络和执行环境的确定性约束。第三层是对某个具体动作的用户授权与可选独立模型复核。Prompt、独立审查模型和工具名称白名单都不能单独替代前两层。允许 bash 或 eval 后，代码可能执行文件或网络动作，必须限制实际环境，而不是只隐藏 edit 工具。

OMP 原生 [审批文档](https://github.com/can1357/oh-my-pi/blob/main/docs/approval-mode.md)明确默认 approvalMode 为 yolo，实际配置可以覆盖默认。当前产品以 rpc --no-ui 启动，原生工具审批如果需要交互则失败关闭，不能直接向 GUI 弹审批卡。补产品审批必须选择受控 host tools 的宿主审批，或 plain rpc-ui 的真实 UI 桥接并验证，不能只增加一个 approval-mode 开关。底层子代理也有 headless 审批语义，父任务能力和预算要明确下传。

也不应把每个 list_bots、每次普通委派都强制弹审批。内部低风险行为应自动进行，跨工作区、扩大数据范围或引入对外副作用时才评估授权。已有合法授权可在作用域内延续，避免把产品做成确认框队列。

### 浏览器、应用连接与工具生态

|---|---|---|---|---|
| I01 | 底层可用工具未形成工作台级能力目录 | 用户不知道 Bot 能做什么 | 每个 Bot 显示启用工具、所需服务和权限状态 | P1 |

| I03 | OMP 浏览器可被模型使用，但 UI 无可视电脑与接管 | 登录、验证码、卡住时用户无法协助 | 浏览器状态预览、请求接管、人工期间暂停输入、明确交还 | P1 |
| I04 | 无产品级 skills 安装、查看和作用域 | 技能继承不透明且用户难编辑 | 显式 Bot 或 Workspace 技能库，版本与来源可查 | P1 |
| I05 | 无业务事件接收端和触发权限 | 自动工作不能由外部事件驱动 | 单独鉴权的 webhook receiver，和管理 API 分离 | P2 |

“先接 500 个应用”不是合适的验收标准。应看两条真实流程是否成功、过期认证是否明确、只读和写入是否分开、审批拒绝后是否停止、撤销后是否仍被后台任务使用。

## 容易误判的“先进性”

多 Bot 不是质量保证。要看任务分解、职责、并行约束、汇总和验收。十二轮群聊也可能只是昂贵的重复讨论。

长上下文不是长期记忆。会话续接、稳定偏好、项目资料、任务状态和权限批准是不同对象。权限不能靠一段被压缩过的聊天重新猜。

本地优先不是安全隔离。数据保存在本机有控制权优势，但模型请求仍会发到提供商，本机工具也可能拥有比云 VM 更广的用户权限。

自动审查不是沙箱。Grok 官方明确说 Auto Review 不审查所有副作用。Muse 把 Sentinel 放在运行环境外，并治理实际网络请求。我们应学习其结构，而不是先复制一个“审查模型”按钮。

常驻进程不是持续服务。托盘解决关窗口，无法解决电脑关机。要在关机后运行，需要用户明确选择常开主机、VPS 或托管执行节点。

## 推荐取舍

| 选项 | 优点 | 代价与风险 | 判断 |
|---|---|---|---|
| 只补聊天 UI | 较快得到流式、停止和搜索 | 任务、权限和后台问题仍未解决 | 作为第一阶段的一部分 |
| 全面复制云代理产品 | 可追求完整多端常驻体验 | 账号、云资源、凭据、网络安全和运维范围过大 | 不作为首轮方向 |
| OMP 为执行引擎，增加任务和授权工作台 | 复用现成接口，保留多模型与本地优势 | 需要认真定义 Task、Run、Scope 和 Action | 推荐 |
| 换 React 或 TypeScript 后再加功能 | 有利于后期模块与类型维护 | 无法直接解决权限和交付，容易先做迁移工程 | 新增状态复杂度确有需要时局部迁移 |
| 全局开启记忆与插件 | 表面快速增加能力 | 重现污染和过宽继承，授权难解释 | 拒绝 |
