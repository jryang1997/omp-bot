## 1. Dots 与 ChatGPT agent / Tasks / ChatGPT Work / Codex 的边界

| 产品 | 触发形态 | 执行体 | 计费口径（官方） |
|---|---|---|---|
| **Dots** | 常驻、跨会话、可自行唤醒+可选定时/事件 | 自己的**云端 computer+browser**；可选接入你的一台本机 | dot 的对话**不计入** ChatGPT 用量；它派发到 Work/Codex 的任务照常计入 |
| ChatGPT agent | 单次任务，tools 菜单/`/agent` 发起 | 虚拟浏览器（截图驱动） | 月消息数：Plus 40 / Pro 400 / Business&Enterprise 40（初发请求才计数） |
| Scheduled tasks（Tasks） | 定时或“受支持事件”触发 | 运行于 ChatGPT / Work | 活跃任务上限：Free&Go 3 / Plus 5 / Business&Edu 10 / Pro&Enterprise 15；事件触发≤30 次/时、720 次/日 |
| ChatGPT Work / Codex | 明确交付物的委派任务 | 本地或云容器、Codex 云环境 | 计入各自用量/额度 |

要点：Dots 复用 ChatGPT/Work/Codex 的底层能力，但**产品概念独立**——把 agent 的“月消息额度”或 Tasks 的“任务上限/事件上限”直接套给 Dots 是错误的。[官方文档] learn.chatgpt.com/docs/dots（“How dots compare with ChatGPT Work and Codex”）；[官方声明] openai.com/index/introducing-dots。三者“谁发起、谁执行、算谁的额度”必须分开陈述。

## 4. 对本地 `omp-bot` 的差距（证据：本仓库 path:line）

`omp-bot` 定位是**本机编排的多 bot 团队**：每 bot 一个 `omp --mode rpc` 子进程，纯 Node 编排器负责花名册、投递、群聊回合（README.md:108-135）。对照 Dots：

- **G1 无常驻云端执行体**。Dots 有 24/7 云 computer+browser；omp-bot 每个 bot 是本机子进程，本机关了就跑不了（README.md:128；src/bot.mjs）。
- **G2 无调度/事件触发**。src 全目录检索 `schedule|cron` **无命中**；Dots 有 recurring + event monitoring。omp-bot 只能“用户来消息才跑”。
- **G3 无审批/动作复核层**。src 检索 `approv|auto-review|sandbox` **无命中**；Dots 有内建规则+自定义规则四档+独立 Auto-review（controls 文档；help 20001529）。omp-bot 的 bot 只要模型决定就直接用 omp 工具执行。
- **G4 无产品级连接器/授权面（底层 omp 运行时本身已有工具/技能/插件/MCP/browser 能力）**。`omp_bot` 自身 src 检索 `plugin|mcp|connector` **无命中**——这些能力由宿主 `omp` 运行时提供，编排层未做产品化的“连接授权管理 + 技能库 + 可见的浏览器接管/产物 UI”。编排层团队工具只有 `message_bot`/`list_bots`（README.md:130）。Dots 经插件接 4,000+ 应用并有平台级授权与治理。**注意**：不能说“产品完全无工具/MCP/浏览器能力”，差距在**产品纳管的授权、技能库与可视化外壳**。
- **G5 记忆被“为隔离而关闭”**。`memory.backend: off` + `autolearn.enabled:false`（src/persona.mjs:75-78），常驻记忆只靠会话续接（README.md:16,165）。这是**有意的安全取舍**（防跨 bot 污染），但结果是没有 Dots 式的“跨会话偏好/决定/在办笔记”，也无“笔记可整体删除”的治理面。
- **G6 无多渠道入口**。入口仅 GUI+CLI，IM 桥“未含”（README.md:168；src/server.mjs:45）。Dots 有 ChatGPT/语音/Slack/Teams/短信。
- **G7 无任务追踪面**。无 Activity/Scheduled/In progress 视图；只有 session 与 usage（README.md:133-135）。群聊回合失败只报错（README.md 快速开始段）。
- **G8 无移动端与通知**。GUI 只听 `127.0.0.1`、假设本机单用户、无鉴权（README.md:169；src/server.mjs:2,45）。
- **G9 治理=单写者锁**。`state.lock`+pid 单写者（src/store.mjs:3,35-82），无多租户/RBAC/合规导出（README.md:166）。
- **G10 安全边界不对等**。omp-bot 的隔离目标是 context/记忆污染（src/persona.mjs:5-14,70-78），**没有**针对工具输出中“指令注入”的动作闸门；Dots 有沙箱+Auto-review+监控暂停。
- **G11 无产物/交付面**。无 artifacts/文件视图；Dots 明确产出文档/软件并保留。
- **G12 恢复力弱**。单个 orchestrator 写（src/store.mjs:59-65），第二实例只读；无 Dots 式的“任务在云环境续跑/换电脑不迁移”。

## 5. 优先级建议与可验收指标

原则：**先补“能安全常驻、可审计、可停止”的最小闭环，再谈生态**。不要为了对齐 Dots 而先堆连接器。

**P0（无则不可托管长任务）**
1. **动作闸门 / 审批层**：在 host tool 调用点前插“策略判定”中间件（allow / ask / handoff 三态），默认对写操作 ask。验收：单测覆盖三态；一条“外发消息”必须产生审批记录；被拒后 bot 不得换路径重试（对齐 auto-review 的“拒绝≠可绕行”语义，见 learn.chatgpt.com/docs/sandboxing/auto-review）。
2. **调度 + 事件触发**：新增 scheduler（至少 cron 式周期）与“事件→投递”适配位。验收：断网/关 GUI 后进程内调度仍按点产出；一条周期任务可 pause/cancel 且与“停当前回合”分离。
3. **可持久、可审计的任务台账**：`Activity`(进行中/等待输入/完成) + `Scheduled`。验收：每条 bot 回合与每次投递产生可查询记录；重启后台账不丢。

**P1（可用性与规模化）**
4. **记忆分层**：把“隔离”与“无用记忆”解耦——为每 bot 提供**独立、可整体删除、默认不跨 bot**的笔记层，而非直接关掉后端。验收：`probe-isolation` 仍证明不 recall/retain 用户共享库；新增断言证明 bot 自己的笔记可跨进程续存、可一键清除。
5. **访问控制 + 远程渠道**：GUI 加鉴权 + 一个 IM 适配（如 Telegram/飞书）映射到 `chatWithBot`/`postToRoom`。验收：未鉴权请求 401；IM 往返一轮闭环有 transcript 证据。
6. **通知面**：回合完成/需要输入/被阻塞三态外发通知（对齐 Dots 的“需要决策才打断”）。验收：三态各触发一次可观测通知。

**P2（对齐 Dots 生态）**
7. **连接器/MCP**：以 MCP 为统一接入（插件即 MCP server + 权限），复用宿主 omp 的既有 MCP 支持而非自研。验收：一个 MCP server 授权→只读/写两档权限可验证；断连不删已得数据（对齐 Dots “断开≠删除”）。
8. **产物面**：暴露文件/产出浏览与保留策略。验收：一次任务产出文件可在 GUI 查看、按策略删除。

**不要做**：在未建审批层前引入云端常驻执行体（会把无闸门的写操作搬上 24/7 通道）；照搬 Dots “4,000+ 应用”式生态而不先做权限与审批。

## 6. 一句话结论

Dots 的护城河不是模型，而是**常驻云端执行体 + 跨渠道/跨会话记忆 + 独立 Auto-review 审批 + 平台级插件与治理**的整套产品化；`omp-bot` 的强项是**本机多 bot 编排与记忆隔离**。差距集中在 G1–G4、G6–G7、G10——且**记忆隔离与审批/调度并不冲突**：可先在保留隔离的前提下补 P0 的审批+调度+台账，再逐层外扩。

### 摘要（<900 字）

截至 2026-10-12，OpenAI dots 在 Pro、Business Premium、Enterprise 灰度开放，企业默认关闭。地区、年龄和计划限制见矩阵。移动应用创建能力有一手文档冲突，当前 docs/dots 明确可在手机创建，help 20001530 仍称不可，本轮未实操裁定。Dots 有云电脑与浏览器，可另接一台本机；后台并行和主动只读研究见官方任务文档。

能力面包含插件连接、ChatGPT、语音、Slack 和 Teams，Teams 有邀请 alpha 限制。短信在帮助页为美国 Pro 有限 beta，部分文案仍写 coming soon，标为来源更新冲突。任务可周期调度或监控支持的事件，Activity 和 Scheduled 管理运行。记忆来自会话、ChatGPT 记忆与私有笔记，单条笔记管理限制见帮助页。

安全/边界：内建规则+自定义规则四档（免问/显式请求时/先问/交回），叠加独立 **Auto-review** 复核外发与改账户动作；改密码、转账必须交回用户；删数据/装未知软件逐次确认；沙箱隔离、可连 4,000+ 应用、监控发现风险可暂停工作。系统卡实测：批量 5 万邮件（含 1.66 万攻击）0 成功、迭代攻击 2638 次 0 成功；持久设定下严重错位率 0.84%、误导性主动输入 0.00%（151 任务）；但“被警告后仍坚持”约 15–17%，5→10 个插入任务使中度越界从 8.6% 升到 19.7%（[系统卡 §12]）。

**与旧产品必须分开**：ChatGPT agent 是单次任务、虚拟浏览器、月消息额度（Plus 40/Pro 400/B&E 40）；Scheduled tasks 是定时/事件任务、活跃上限 3/5/10/15；Dots 的对话**不**计入 ChatGPT 限额，只有它派发到 Work/Codex 的任务才计（[help 11752874]、[help 10291617]、[docs/dots]）。把 agent 的额度或 Tasks 的上限套给 Dots 是事实错误。

与 omp-bot 的差距在产品管理层。OMP 本身已有工具、技能、插件与浏览器能力；工作台缺持久任务、调度、可见审批、连接器授权、成果与多渠道管理。memory.backend off 保留了共享库隔离，但 --continue 仍可续接历史，因此不能说完全没有跨会话记忆。

**优先级**：P0 先补“动作闸门（allow/ask/handoff）+调度与事件触发+可审计任务台账”，这是托管长任务的最小闭环；P1 解耦“隔离”与“无用记忆”，给每 bot 独立可删笔记层，并加 GUI 鉴权与一个 IM 渠道、三态通知；P2 以 MCP 统一连接器、补产物面。**不要**在无审批层时先上云端常驻执行体或堆生态。验收要点：审批三态单测、被拒不得改道重试、断 GUI 仍按点调度、重启台账不丢、隔离断言与“笔记可跨进程续存且可整体清除”并存、未鉴权 401、IM 一轮闭环有 transcript 证据。
